# API бронирования помещений

Система бронирования общих помещений (переговорных): просмотр помещений,
бронирование времени, подтверждение и отмена броней. Накладки невозможны —
проверка атомарная (транзакция + блокировка строки ресурса + уникальный индекс).

- **Backend**: Python, FastAPI, psycopg2
- **БД**: embedded PostgreSQL (пакет `pgserver`) — ставится через pip,
  данные лежат в папке `pgdata\` (создаётся сама при первом запуске, в git не входит)
- **Время**: ISO 8601 (`2026-10-26`, `09:00:00`, `2026-10-26T09:00:00+05:00`)

## Жизненный цикл брони

```
POST /bookings            → PENDING    (создана, время уже занято)
POST /bookings/{id}/confirm?user_id=1 → CONFIRMED
POST /bookings/{id}/cancel?user_id=1  → CANCELLED  (слот освобождается)
```

Подтверждать и отменять может **только владелец** (`user_id` сверяется с бронью):
чужая бронь → `403`, повторное подтверждение/отмена → `409`.
Слот занимают все статусы, кроме `CANCELLED`.

## Запуск

```powershell
pip install fastapi "uvicorn[standard]" pgserver psycopg2-binary
python init_db.py            # 1-й раз: initdb + старт PG + таблицы + сид (несколько секунд)
uvicorn app:app --reload     # API: http://127.0.0.1:8000
```

Swagger: **http://127.0.0.1:8000/docs** — все эндпоинты можно дёргать прямо из браузера
(«Try it out»).

`init_db.py` идемпотентен: перезапуск безопасен (ничего не дублирует).

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/resources` | список помещений (id, name, area, capacity, equipment, working_hours) |
| GET | `/settings` | рабочие часы и шаг слота: `{"working_hours": {...}, "periods_count": 14, "now": "..."}` |
| GET | `/times` | справочник периодов брони (сеансы): id, start_time, end_time, duration_minutes |
| GET | `/availability` | **свободные** периоды помещения на дату `?resource_id=1&booking_date=YYYY-MM-DD` (занятые и прошедшие не попадают) |
| GET | `/bookings` | список броней; фильтры: `?user_id=`, `?booking_date=YYYY-MM-DD`, `?date_from=`, `?date_to=`, `?resource_id=`; в ответе `starts_at`/`ends_at` в ISO 8601 |
| POST | `/bookings` | создать бронь → `201`, статус `PENDING`; время — `time_id` / `time_ids` или `starts_at` + `ends_at` (ISO 8601) |
| POST | `/bookings/{id}/confirm?user_id=1` | подтвердить бронь (только владелец) → `CONFIRMED` |
| POST | `/bookings/{id}/cancel?user_id=1` | отменить бронь (только владелец) → `CANCELLED`; повторно → `409` |
| GET | `/users` | список пользователей; фильтры: `?phone=`, `?name=` (вход по номеру/имени) |
| POST | `/users` | регистрация `{name, phone}` → 201; телефон занят → 409 |

## Периоды брони (как сеансы в кинотеатре)

Время брони выбирается **из справочника периодов**, а не произвольное:

- таблица `Время` = справочник: 14 периодов по часу, 08:00–09:00 … 21:00–22:00
  (заливается в `init_db.py`, как `Статус` и `Ресурс`);
- `Бронь.ID_Время` ссылается на выбранный период; одна строка `Бронь` = один период;
- `POST /bookings` принимает `time_id` (один период) **или `time_ids` (несколько сразу)**
  → произвольное время забронировать нельзя, старый формат `start_time`/`end_time` → 422;
- `GET /times` отдаёт весь справочник — фронт по нему рисует сетку расписания;
- `GET /availability?resource_id=…&booking_date=…` отдаёт **только свободные** периоды
  (занятые и прошедшие отсутствуют) — готовый список для выпадающего меню;
- `GET /settings` и блок `working_hours` в `GET /resources` читаются из БД
  (источник истины — таблица `Время`).

## Время в формате ISO 8601

- дата — `"2031-03-03"`, время слота — `"09:00:00"`, момент — с часовым поясом;
- в ответах `GET /bookings`, `POST /bookings`, `confirm`, `cancel` есть полные метки
  `starts_at` / `ends_at`: `"2031-03-03T09:00:00+05:00"` (пояс сервера);
- `GET /settings` → `now` тоже с поясом: `"2026-10-25T21:51:15+05:00"`;
- создать бронь можно интервалом вместо id периодов:

```json
POST /bookings
{"user_id": 1, "resource_id": 1,
 "starts_at": "2031-03-03T09:00:00+05:00",
 "ends_at":   "2031-03-03T11:00:00+05:00"}
```

Сервер сам раскладывает интервал на периоды справочника. Требования:
оба поля вместе, `ends_at > starts_at`, один день, границы совпадают с сеткой
периодов (`GET /times`), иначе `400`. Пояс можно не указывать — время считается
локальным.

## Несколько периодов подряд (выделение диапазона)

Пользователь выделяет мышкой 2–3 часа подряд, фронт отправляет **одним** запросом:

```json
POST /bookings
{"user_id": 1, "resource_id": 1, "booking_date": "2031-03-03", "time_ids": [8, 9, 10]}
```

- порядок id любой, дубли игнорируются; в БД создаётся по строке на каждый период;
- **всё или ничего**: проверка накладок и вставка идут в одной транзакции под
  `SELECT … FOR UPDATE` по строке ресурса. Занят хоть один период → `409`,
  в `detail` перечислены занятые (`"накладка: уже занято 10:00-11:00"`),
  ни одна бронь не создаётся;
- прошедший период в пакете → `400` целиком (частичная бронь сломала бы ожидание
  «выделил 9–11 — получил 9–11»);
- ответ: `id`/`ids` (все созданные id), `count`, `time_ids` по порядку,
  `start_time`/`end_time` (начало первого и конец последнего), `starts_at`/`ends_at`,
  `bookings` — список созданных строк;
- отмена — по одной строке: `POST /bookings/{id}/cancel?user_id=…` для каждого id из `ids`;
- старый формат с одним `time_id` работает как раньше.

`GET /availability` — чтобы занятых вариантов вообще не было в списке:

```
GET /availability?resource_id=1&booking_date=2031-03-03
→ [{"id": 3, "start_time": "09:00:00", "end_time": "10:00:00"},
   {"id": 8, "start_time": "10:00:00", "end_time": "11:00:00"}, ...]
```

Занятость считается по пересечению периодов, `CANCELLED` слот не занимает,
прошедшие периоды тоже не попадают. Помещения нет → `404`, всё занято → `[]`.

## Расписание (неделя / месяц)

`GET /bookings` принимает **диапазон дат** — для вкладки «неделя» и «месяц» хватает
одного запроса вместо 7/31:

```
GET /bookings?date_from=2026-10-19&date_to=2026-10-25            # неделя
GET /bookings?date_from=2026-10-01&date_to=2026-10-31            # месяц
GET /bookings?date_from=2026-10-01&date_to=2026-10-31&resource_id=1
```

- `date_from` / `date_to` — включительно, границы можно не указывать по одной;
  `date_from > date_to` → 400.
- Фильтры комбинируются по «И»: `user_id` + `date_from/date_to` + `resource_id`.
- `booking_date` (точная дата) можно совмещать с диапазоном — сработает пересечение.
- В ответе у каждой брони есть `user_id`, `time_id`, `status`, `starts_at`/`ends_at`
  → фронт красит «свои» слоты синим, чужие — красным, `CANCELLED` игнорирует
  (`PENDING` и `CONFIRMED` занимают слот одинаково).

## Отрисовка расписания (фронт)

1. `GET /times` — сетка дня: 14 периодов по часу (id, start_time, end_time).
2. `GET /bookings?date_from=…&date_to=…&resource_id=N` — занятость за период.
3. Период занят, если есть бронь с этим `time_id` и `status != CANCELLED`:
   своя — синяя, чужая — красная, свободная — белая, начавшаяся раньше `now`
   из `/settings` — серая и не кликается.
4. Список времени для брони — `GET /availability?resource_id=N&booking_date=…`:
   в нём уже только свободные периоды (занятые/прошедшие отсутствуют), вычитать
   ничего не нужно. Выделение нескольких подряд → `time_ids` в `POST /bookings`,
   одна атомарная операция.

## Коды ответов

`201` создано · `200` ок · `400` плохой ввод (время в прошлом, `date_from > date_to`,
не указан период, интервал не по сетке) ·
`403` чужая бронь (подтверждение/отмена не владельцем) ·
`404` не найдено (бронь, помещение, пользователь, период) ·
`409` накладка / повторное подтверждение / повторная отмена / дубль телефона ·
`422` ошибка валидации (нет обязательного поля, например `user_id` у confirm/cancel).
Формат ошибок: `{"detail": "..."}`.

## Как устроено

- `db.py` — embedded PostgreSQL: сервер поднимается при первом обращении
  (initdb + старт) и останавливается вместе с последним процессом
- `init_db.py` — создаёт БД `booking`, таблицы и сид: 3 помещения,
  2 пользователя (Иван, Мария), статусы PENDING/CONFIRMED/CANCELLED,
  справочник периодов (14 периодов по часу, 08:00–22:00), уникальный индекс
  `uq_booking_active_slot`; старый статус ACTIVE миграцией переводится в CONFIRMED
- `app.py` — API; атомарность накладок: в `POST /bookings` строка ресурса
  блокируется (`SELECT ... FOR UPDATE`) до конца транзакции — параллельные
  запросы по одному помещению выполняются строго по очереди. Пакет периодов
  (`time_ids` / интервал ISO 8601) проверяется и вставляется в той же транзакции
  одним `INSERT ... SELECT` → всё или ничего
- уникальный частичный индекс `uq_booking_active_slot` на
  (`ID_Ресурс`, `Дата`, `ID_Время`) `WHERE "ID_Статус" <> CANCELLED` — вторая
  линия защиты: дубль активной брони не запишется даже в обход проверки
- таблица `Время` — справочник периодов; бронь ссылается на один период
  (`Бронь.ID_Время`), диапазон «с 9 до 11» = две строки `Бронь`
- `GET /availability` — свободные периоды на дату: `NOT EXISTS` по активным
  броням (пересечение периодов) + отсечение прошедшего времени
- Отменённые брони при проверке накладок не учитываются
- `.gitignore` — `pgdata/`, `__pycache__/`, `*.db`, `.venv/` в репозиторий не попадают


CORS разрешён для всех origin'ов (локальная разработка); при выносе
на реальный домен список сузить в `app.py`.

Авторизации нет: вход — поиск аккаунта по телефону и имени (`GET /users`),
фронт хранит id пользователя локально.
