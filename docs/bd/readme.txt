API бронирования помещений

Система бронирования общих помещений (переговорных): просмотр помещений,
бронирование времени, подтверждение и отмена броней. Время брони выбирается
из справочника периодов (как сеансы в кинотеатре: 08:00-09:00, 09:00-10:00,
..., 21:00-22:00) либо задаётся интервалом в ISO 8601.
Накладки невозможны — проверка атомарная (транзакция + блокировка строки
ресурса + уникальный индекс на активную бронь).

Backend: Python, FastAPI, psycopg2
БД: embedded PostgreSQL (пакет pgserver) — ставится через pip, данные
лежат в папке pgdata\ (создаётся сама при первом запуске, в git не входит).

Жизненный цикл брони:
  POST /bookings              → PENDING    (создана, слот занят)
  POST /bookings/{id}/confirm → CONFIRMED  (только владелец)
  POST /bookings/{id}/cancel  → CANCELLED  (только владелец, слот свободен)

ЗАПУСК

  pip install fastapi "uvicorn[standard]" pgserver psycopg2-binary bcrypt
  $env:ADMIN_PASSWORD="свой_пароль"   # необязательно: без неё генерируется
  python init_db.py            # 1-й раз: initdb + старт PG + таблицы + сид
  uvicorn app:app --reload     # API: http://127.0.0.1:8000

Swagger: http://127.0.0.1:8000/docs — все эндпоинты можно дёргать прямо
из браузера (кнопка «Try it out»).

init_db.py идемпотентен: перезапуск безопасен (ничего не дублирует).

ЭНДПОИНТЫ

GET  /version        (и то же самое по /api/version)
    версия продукта и дата сборки — для иконки «i» на фронте и для
    баг-репортов (на какой сборке найден дефект):
    {"product": "Система бронирования помещений",
     "version": "1.0.0",
     "build_date": "2026-11-01",
     "build_date_label": "01.11.2026",
     "support": {"name": "Техническая поддержка",
                 "email": "support@booking-system.ru"}}
    База данных не используется: ответ не зависит от данных и не требует
    заполненного справочника периодов.
    Два пути на одну функцию: /version — по стилю контракта (базовый URL
    без /api), /api/version — как в задаче/тест-кейсе. В Swagger виден
    только /version.
    build_date — машинный ISO (YYYY-MM-DD), build_date_label — готовая
    строка ДД.ММ.ГГГГ для попапа, как в макете («Сборка: 01.11.2026»).
    ⚠ Версия и дата сборки — константы VERSION / BUILD_DATE в начале
    app.py: при каждом релизе менять BUILD_DATE руками (YYYY-MM-DD),
    build_date_label пересчитается сам; версия в Swagger (version=
    у FastAPI) берётся из VERSION — она же и есть версия продукта.

GET  /settings
    настройки расписания:
    {"working_hours": {"start_time": "08:00", "end_time": "22:00",
                        "slot_minutes": 60},
     "periods_count": 14,
     "now": "2026-10-25T21:51:15+05:00"}
    working_hours — границы рабочего дня и шаг слота (одни и те же для всех
    помещений, берутся из справочника периодов в БД). now — текущее время
    сервера (для «прошедшее время серым»).

GET  /times
    справочник периодов брони («сеансы») — как в кинотеатре:
    [{"id": 7, "start_time": "08:00:00", "end_time": "09:00:00",
      "duration_minutes": 60},
     {"id": 3, "start_time": "09:00:00", "end_time": "10:00:00"}, ...]
    Всего 14 периодов: 08:00-09:00, 09:00-10:00, ..., 21:00-22:00.
    Это ТА ЖЕ таблица "Время" в базе, и id периодов постоянные.
    Время в ISO 8601 (HH:MM:SS), duration_minutes — длина периода.
    Фронт по этому списку рисует сетку расписания.

GET  /availability?resource_id=1&booking_date=2031-03-03
    ГОТОВЫЙ список свободного времени на дату — занятые и прошедшие
    периоды в нём ОТСУТСТВУЮТ (для выпадающего списка времени):
    [{"id": 8, "start_time": "09:00:00", "end_time": "10:00:00"},
     {"id": 3, "start_time": "10:00:00", "end_time": "11:00:00"}, ...]
    Отменённые брони слот не занимают. Помещения нет → 404.
    Пустой список [] = на эту дату всё занято/прошло.
    Для СЕТКИ расписания (где нужны и занятые ячейки) по-прежнему
    используется GET /bookings.

GET  /resources
    список помещений: id, name, area, capacity, equipment,
    working_hours (тот же блок, что в /settings)

GET  /bookings
    список броней; фильтры (необязательные):
    ?user_id=1                        — брони пользователя
    ?booking_date=YYYY-MM-DD          — расписание дня
    ?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD
                                     — диапазон дат (вкладка «неделя»/«месяц»),
                                       границы включаются, можно указать одну
    ?resource_id=2                    — одно помещение
    ?search=иван                      — подстрока в имени заказчика
                                        (регистр не важен, ищет по «Имя»)
    ?sort=start | start_desc          — порядок по времени начала;
                                        по умолчанию start (по возрастанию)
    Фильтры комбинируются по «И». date_from > date_to → 400. Неверный
    sort → 400. Сортировка: сначала дата, затем время начала.
    В ответе каждой брони есть user_id, time_id, status (PENDING/CONFIRMED/
    CANCELLED), start_time/end_time, а также starts_at/ends_at — полные
    метки ISO 8601 с часовым поясом: "2031-03-03T09:00:00+05:00".
    Имя ресурса — в поле resource (resource_id в ответ не отдаётся).
    Внимание: отменённые брони (status = CANCELLED) тоже в ответе — их надо
    отфильтровывать при отрисовке расписания.

GET  /summary?date_from=2031-03-01&date_to=2031-03-31[&resource_id=1]
    СВОДКА ЗАНЯТЫХ ЧАСОВ по каждому помещению за период (для блока сводки):
    [{"resource_id": 1, "resource": "Переговорная А",
      "hours": 12.0, "bookings_count": 12},
     {"resource_id": 2, "resource": "Переговорная Б",
      "hours": 3.0,  "bookings_count": 3}]
    - обе даты ВКЛЮЧАЮТСЯ;
    - часы = сумма длительностей периодов (сейчас каждый период — 1 час);
    - учитываются PENDING и CONFIRMED; CANCELLED в сумму НЕ входит;
    - помещения без броней в период (0 часов) в ответ не попадают;
    - ?resource_id=N — сводка по одному помещению;
    - date_from > date_to → 400; даты не переданы/битые → 422.

POST /bookings
    создать бронь — ОДИН период или НЕСКОЛЬКО сразу, тело:
    {"user_id": 1, "resource_id": 1, "booking_date": "2031-03-03",
     "time_ids": [8, 9]}
       — несколько периодов: 09:00-10:00 и 10:00-11:00 (id из /times);
         порядок любой, дубли игнорируются, всё создаётся АТОМАРНО:
         либо все периоды, либо ни один (занят хоть один → 409 и в базу
         не пишется ничего);
    {"user_id": 1, "resource_id": 1, "booking_date": "2031-03-03",
     "time_id": 8}
       — один период (старый формат, работает);
    {"user_id": 1, "resource_id": 1,
     "starts_at": "2031-03-03T09:00:00+05:00",
     "ends_at":   "2031-03-03T11:00:00+05:00"}
       — интервал в ISO 8601: сервер сам раскладывает его на периоды
         справочника. Нужны оба поля, один день, ends_at > starts_at,
         границы совпадают с сеткой /times, иначе 400. Пояс можно не
         указывать (тогда время считается локальным).
    ВАЖНО: бронируется ПЕРИОД или интервал, а не произвольное время;
    поле booking_date нужно только вместе с time_id/time_ids.
    → 201. Статус новой брони — PENDING (слот уже занят).
      В ответе: id (первая бронь), ids (все id), count, time_ids
      (периоды по порядку), start_time/end_time (начало первого и конец
      последнего периода), starts_at/ends_at (ISO 8601), bookings — список
      созданных броней:
      [{"id": 10, "ids": [10, 11], "count": 2, "status": "PENDING", ...,
        "time_ids": [8, 9], "start_time": "09:00:00",
        "end_time": "11:00:00",
        "starts_at": "2031-03-03T09:00:00+05:00",
        "ends_at": "2031-03-03T11:00:00+05:00",
        "bookings": [{"id": 10, "time_id": 8, "start_time": "09:00:00",
                      "end_time": "10:00:00", ...}, ...]}]
    Накладка (хоть один период занят) → 409, в detail перечислены занятые:
      {"detail": "накладка: уже занято 10:00-11:00"}
    Нельзя бронировать прошедшее время → 400 (тоже всё или ничего).
    Несуществующий time_id/time_ids → 404. Период не указан → 400.
    Отмена пакета — по одной брони (POST /bookings/{id}/cancel?user_id=…
    для каждого id из ids).

POST /bookings/{id}/confirm?user_id=1
    подтвердить бронь: PENDING → CONFIRMED. Подтверждать может ТОЛЬКО
    владелец. Чужая бронь → 403. Уже подтверждена → 409.
    Отменена → 409. Брони нет → 404. Без user_id → 422.
    Период брони уже начался (идёт прямо сейчас) или прошёл → 409:
      {"detail": "нельзя подтвердить прошедшую бронь: 26.10.2026 08:00-09:00
                 (период уже начался)"}
    Ответ: {"id": 10, "status": "CONFIRMED", "date": "...",
             "start_time": "09:00:00", "end_time": "10:00:00",
             "starts_at": "...", "ends_at": "..."}

POST /bookings/{id}/cancel?user_id=1
    отменить бронь: статус становится CANCELLED, слот освобождается.
    Отменять может ТОЛЬКО владелец — или администратор (role = ADMIN),
    который может отменить ЛЮБУЮ бронь. Чужая бронь обычному пользователю
    → 403. Повторная отмена → 409 (а не 200). Брони нет → 404.
    Без user_id → 422. Прошедшую бронь не отменяет никто (в том числе
    администратор) — см. ниже.
    Период брони уже начался (идёт прямо сейчас) или прошёл → 409:
      {"detail": "нельзя отменить прошедшую бронь: 26.10.2026 08:00-09:00
                 (период уже начался)"}
      «Начался» = начало периода наступило: для 08:00-09:00 отмена
      запрещена уже в 08:00:00 (и в 08:01, пока период идёт).
    Ответ: {"id": 10, "status": "CANCELLED", ...}

СТАТУСЫ БРОНИ

PENDING    — создана, ждёт подтверждения (слот занят)
CONFIRMED  — подтверждена владельцем (слот занят)
CANCELLED  — отменена (слот свободен)
Старый статус ACTIVE упразднён; init_db.py переводит такие брони в CONFIRMED.

РОЛИ ПОЛЬЗОВАТЕЛЕЙ

USER   — обычный пользователь: бронирует, видит в «Моих бронях» только
         свои брони без отменённых и без прошедших; отменяет только свои;
         поиск по заказчику и сводка ему недоступны (403).
ADMIN  — администратор: видит все брони всех пользователей, включая
         прошедшие и отменённые; может отменить любую бронь (кроме
         прошедшей); доступны поиск по заказчику и /summary.
         Создаётся init_db.py, через регистрацию не получить.
Роль отдаётся полем role в GET /users и POST /users.

ВХОД АДМИНИСТРАТОРА

POST /auth/admin-login  {"fio": "admin", "password": "..."}
    также принимается {"phone": "+70000000000", "password": "..."}
    → 200 {"token": "...", "expires_at": "...", "user": {"id","name","role"}}
    «Кто ты» — имя (fio, без учёта регистра) или телефон (phone, точно).
    Неверное имя/пароль → 401 (ответ одинаковый, чтобы не подсказывать,
    какие аккаунты существуют). Обычному пользователю и аккаунту без
    пароля → тоже 401. Срок жизни токена — 12 часов.

POST /auth/admin-logout?token=...
    → 200 {"logged_out": true} — токен отозван, повторно не работает.

Где принимается токен (?token=...):
    GET  /bookings  — без токена нельзя смотреть все брони (403) и
                      пользоваться поиском по заказчику (403);
    GET  /summary   — только с токеном (403 без него);
    POST /bookings/{id}/cancel — с токеном можно отменить ЧУЖУЮ бронь.

Пароль администратора: берётся из переменной окружения ADMIN_PASSWORD
при запуске init_db.py. Если переменной нет — сгенерируется случайный и
будет напечатан один раз (сохраните его). Сменить пароль: удалить хэш и
перезапустить init_db.py с нужным ADMIN_PASSWORD:
    UPDATE "Пользователь" SET "ПарольHash" = NULL WHERE "Роль" = 'ADMIN';

ОГРАНИЧЕНИЯ НА ПОЛЬЗОВАТЕЛЯ

Имя и телефон проверяются дважды — в API (422 с понятным текстом) и
в PostgreSQL (CHECK-констрейнты, даже при записи в обход API):
    имя:      только буквы (кириллица/латиница), пробел и дефис;
              от 2 до 100 символов; цифры запрещены;
    телефон:  '+7' и ровно 10 цифр  (+7XXXXXXXXXX).
На входе 8XXXXXXXXXX и «+7 (XXX) XXX-XX-XX» нормализуются в +7XXXXXXXXXX.
Телефон уникален (индекс uq_user_phone).

ВРЕМЯ СОЗДАНИЯ БРОНИ

Время создания брони ("Создана") ставит СЕРВЕР в момент INSERT
(DEFAULT NOW(), время машины, на которой запущен API). Клиент передать
его не может. В ответах API — поле created_at (ISO 8601 с часовым поясом).

GET  /users
    список пользователей (id, name, phone, role); фильтры для «входа»:
    ?phone=+79001112233&name=Иван   — ищет аккаунт по номеру и имени
    Пустой список = аккаунта нет.
    role — роль пользователя: "USER" (обычный) или "ADMIN" (администратор).
    Фронт по этому полю решает, какой интерфейс рисовать: у ADMIN —
    вкладка «Брони» (все брони всех пользователей, включая прошедшие)
    и сводка /summary; у USER — «Мои брони» (только свои, без прошедших).

POST /users
    регистрация, тело: {"name": "Иван", "phone": "+79001112233"}
    → 201 (в ответе id и role). Роль всегда USER — стать администратором
    через регистрацию нельзя. Телефон уже занят → 409.
    Администратор создаётся только init_db.py: имя admin, телефон
    +70000000000 (номер занят, поэтому зарегистрировать его нельзя).

КАК РИСОВАТЬ РАСПИСАНИЕ (для фронта)

1) GET /times — список периодов (id, start_time, end_time). Это и есть
   сетка: 14 ячеек в строке дня, по часу, 08:00-22:00.
2) GET /bookings?date_from=...&date_to=...&resource_id=N — все брони за
   период (неделя = один запрос, месяц = один запрос).
3) Ячейка периода (time_id) занята, если есть бронь с этим time_id
   и статусом PENDING или CONFIRMED. Своя бронь (user_id совпадает с id
   вошедшего) — синяя, чужая — красная, свободная — белая, период в прошлом
   (start_time меньше now из /settings) — серый и не кликается.
4) Свободное время для выпадающего списка = GET /availability
   (?resource_id=N&booking_date=...). Занятые и прошедшие периоды в этом
   ответе отсутствуют — можно сразу рисовать список, ничего не вычитая.
   Считает только АКТИВНЫЕ брони (CANCELLED слот не занимает).
5) Бронь = 1 период (1 час) в БД, но клиент может отправить несколько
   периодов одним POST /bookings (time_ids) — например выделил мышкой
   с 9 до 11, ушли id двух часов, создались две брони одной операцией.
   Несколько подряд периодов = несколько строк в "Бронь" с общим user_id,
   resource_id, date; сервер сам проверяет накладки по всем сразу.

ПЕРЕНОС БРОНИ

Отдельного эндпоинта переноса НЕТ. Клиент делает так:
  1) POST /bookings — новая бронь на новую дату/период;
  2) POST /bookings/{id}/cancel — отмена старой;
  3) если шаг 2 вернул ошибку — откат: отменить только что созданную
     (POST /bookings/{новый_id}/cancel), иначе получится дубль.
Это две независимые транзакции БД, не атомарно.
Прошедшую бронь перенести нельзя: шаг 2 вернёт 409 «нельзя отменить
прошедшую бронь» (период уже начался), клиент откатит новую.

КОДЫ ОТВЕТОВ

201 — создано
200 — ок
400 — плохой ввод (время в прошлом, date_from > date_to, период не указан,
      интервал не совпадает с сеткой периодов, ends_at <= starts_at,
      sort не из списка start/start_desc)
403 — чужая бронь (подтверждение/отмена не владельцем)
404 — не найдено (бронь, помещение, пользователь, период)
409 — накладка (хоть один из выбранных периодов занят) / повторное
      подтверждение / повторная отмена / дубль телефона / период брони
      уже начался или прошёл (confirm и cancel)
422 — ошибка валидации (не так формат, нет полей, нет user_id у confirm/cancel)

Формат ошибок: {"detail": "текст"}.

КАК УСТРОЕНО

- db.py — embedded PostgreSQL: сервер поднимается при первом обращении
  (initdb + старт) и останавливается вместе с последним процессом
- init_db.py — создаёт БД booking, таблицы и сид: 3 помещения,
  3 пользователя (админ: имя admin, телефон +70000000000; Иван и Мария — USER),
  статусы PENDING/CONFIRMED/CANCELLED,
  справочник периодов (14 периодов по часу, 08:00-22:00), уникальный индекс
  uq_booking_active_slot; статус ACTIVE из старых данных переводится в CONFIRMED
- Колонка «Роль» у пользователя: миграция ADD COLUMN IF NOT EXISTS (старым
  пользователям ставится USER), CHECK на значения USER/ADMIN
- app.py — API; атомарность накладок: в POST /bookings строка ресурса
  блокируется (SELECT ... FOR UPDATE) до конца транзакции — параллельные
  запросы по одному помещению выполняются строго по очереди.
  Несколько периодов (time_ids или интервал ISO 8601) проверяются и
  вставляются в ТОЙ ЖЕ транзакции (один INSERT ... SELECT) — пакет
  создаётся целиком или никак
- Уникальный частичный индекс uq_booking_active_slot на
  (ID_Ресурс, Дата, ID_Время) WHERE ID_Статус <> CANCELLED — вторая линия
  защиты от дублей, даже в обход проверки в коде
- Таблица "Время" — справочник периодов; бронь ссылается на один период
  (Бронь.ID_Время). Произвольное время забронировать нельзя
- Отменённые брони при проверке накладок не учитываются
- Прошедшее время: локальное время сервера. Создание брони на прошедший
  период → 400; отмена и подтверждение — только ДО начала периода
  (_period_started: бронь 08:00-09:00 «началась» уже в 08:00:00), иначе 409
- pgdata/ и локальные *.db в репозиторий не входят (.gitignore)
