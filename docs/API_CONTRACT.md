# API Contract — Система бронирования

**Версия:** 1.7  
**Дата:** 2026-11-17  
**Базовый URL:** `http://127.0.0.1:8000` (без префикса `/api/v1`)  
**Реализация:** `docs/bd/app.py` (API `0.7.0`)  
**Swagger:** `http://127.0.0.1:8000/docs`  
**Формат ошибок:** `{"detail": "..."}` (или массив ошибок валидации FastAPI)

> Контракт описывает фактическое поведение кода на `main`. При расхождении код приоритетнее — сразу правьте этот файл.

---

## Статусы брони

| Статус | Смысл | Слот |
|--------|--------|------|
| `BOOKED` | Забронирована | занят |
| `CLOSED` | Закрыта — период закончился | занят |
| `CANCELLED` | Отменена | свободен |

Жизненный цикл: `POST /bookings` → сразу **BOOKED** (подтверждение не требуется); после окончания периода бронь автоматически переходит в **CLOSED**; из BOOKED → `POST …/cancel` → **CANCELLED**.  
Слот занимают `BOOKED` и `CLOSED`. Старые статусы `PENDING`, `CONFIRMED`, `ACTIVE` **не используются** — при `init_db.py` переводятся в `BOOKED`.

---

## Модель времени

- Рабочий день разбит на периоды таблицы «ВременнойПериод» (`GET /times`).
- Бронь всегда привязана к одному или нескольким `time_id` (периодам сетки).
- Способы указать время при создании:
  1. `booking_date` + `time_id` **или** `time_ids[]`
  2. `starts_at` + `ends_at` (ISO 8601) — должны лечь на сетку, один день, без разрывов
- Стык слотов (конец одного = начало другого) **не** считается накладкой.
- Несколько периодов в одном `POST /bookings` создаются **атомарно** (все или ни один) под `FOR UPDATE` ресурса.

**Перенос:** отдельного эндпоинта нет. Клиент: создать новую бронь → отменить старую (с компенсирующим откатом новой при ошибке). Это не одна транзакция БД.

## Авторизация (ограничение спринта)

Серверной авторизации нет. Владелец передаётся query-параметром `user_id` на `cancel`. Клиент обязан слать id текущего пользователя; подделать чужой id технически можно.

## Роли пользователей

| Роль | Права |
|------|-------|
| `USER` | Регистрируется сам. «Мои брони» — только свои, без отменённых и прошедших. Отменяет только свои. Поиск по заказчику и `/summary` — 403. |
| `ADMIN` | Создаётся `init_db.py` (имя `admin`, телефон `+70000000000`, пароль из `ADMIN_PASSWORD`). Видит все брони всех пользователей (включая прошедшие и отменённые), может отменить любую (кроме прошедшей). Доступны `search` и `/summary`. |

Роль отдаётся полем `role` в `GET /users` и `POST /users`; через `POST /users` выставляется только `USER`.

## Вход администратора

### `POST /auth/admin-login`
Тело: `{ "phone": "+70000000000", "password": "..." }`  
200: `{ token, expires_at, user { id, name, role } }` — токен на 12 часов.  
401 «неверный телефон или пароль» — для неверного пароля, обычного пользователя и несуществующего аккаунта (ответ одинаковый).

### `POST /auth/admin-logout?token=`
200: `{ logged_out: true|false }` — токен отозван.

Токен передаётся query-параметром `token` в: `GET /bookings` (все брони + `search`), `GET /summary`, `POST /bookings/{id}/cancel` (чужая бронь).

## Эндпоинты

### `GET /`
Редирект на `/docs`.

### `GET /settings`
200: `working_hours { start_time, end_time, slot_minutes }` (строки `"HH:MM"`), `periods_count`, `now` (ISO с таймзоной).

### `GET /times`
200: массив `{ id, start_time, end_time, duration_minutes }`.

### `GET /availability?resource_id=&booking_date=`
Свободные **и непрошедшие** периоды на дату.  
200: `{ id, start_time, end_time }[]`  
404 — ресурс не найден; 422 — невалидные параметры.

### `GET /resources`
200: `{ id, name, area, capacity, equipment, working_hours { start_time, end_time, slot_minutes } }[]`

### `GET /users?phone=&name=`
Фильтры необязательны, точное совпадение. 200: список пользователей `{ id, name, phone, role }`.  
`role` — `USER` (обычный) или `ADMIN` (администратор). Фронт по ней выбирает интерфейс.

### `POST /users`
Тело: `{ "name": "...", "phone": "..." }`.  
`name` — буквы (кириллица/латиница), пробел и дефис, от 2 до 100 символов; `phone` — `+7XXXXXXXXXX` (`8XXXXXXXXXX` приводится к `+7…`).  
201 — создан (`{ id, name, phone, role }`, роль всегда **`USER`**); 409 — телефон уже есть; 422 — невалидное имя/телефон.  
Администратор создаётся только `init_db.py`, через регистрацию роль не выставить.

### `GET /bookings`
Query (все необязательные): `user_id`, `booking_date`, `date_from`, `date_to`, `resource_id`, `search`, `sort`, `token`.  
`search` — подстрока в имени заказчика, регистр не важен (`ILIKE %…%`). Ресурс и диапазон дат можно комбинировать.  
`sort` — `start` (по умолчанию, по возрастанию) или `start_desc`; сортировка по дате, затем по времени начала.  
`token` — токен администратора: снимает ограничение «только свои» и открывает `search`.  
200: `{ id, user_id, user, resource, status, time_id, start_time, end_time, date, starts_at, ends_at, created_at }[]`  
`created_at` — время создания брони по часам сервера (не передаётся клиентом).  
**Нет** поля `resource_id` в строке — только имя `resource`.  
400 если `date_from` > `date_to` или `sort` не из списка; 403 если без `token` не указан `user_id` или запрошен `search`.

### `GET /summary?date_from=&date_to=[&resource_id=][&token=]`
Сводка занятых часов по каждому ресурсу за период; обе даты включительно. **Только с токеном администратора** (403 без него).  
Часы = сумма длительностей периодов из «Время» (`end_time − start_time`). Учитываются `BOOKED` и `CLOSED`, `CANCELLED` не входит. Ресурсы с 0 часов не возвращаются.  
200: `{ resource_id, resource, hours, bookings_count }[]`  
400 если `date_from` > `date_to`; 403 без токена администратора; 422 если параметры дат не переданы/невалидны.

### `POST /bookings`
Тело (минимум):
```json
{
  "user_id": 1,
  "resource_id": 1,
  "booking_date": "2026-10-27",
  "time_id": 3
}
```
Альтернативы: `time_ids: [3,4]` или `starts_at`/`ends_at` вместо даты+time_id.

**Своя бронь на это же время в другом помещении.** Если у пользователя уже есть бронь на ту же дату и те же периоды в **другом** помещении, без явного подтверждения возвращается 409:

```json
{
  "detail": "у вас уже есть бронь на это время: Переговорная А (10:00:00-11:00:00). Чтобы забронировать ещё и это помещение, повторите запрос с allow_overlap_own=true",
  "conflict": "own_overlap",
  "conflicts": [
    { "resource": "Переговорная А", "resource_id": 1, "time_id": 3,
      "start_time": "10:00:00", "end_time": "11:00:00" }
  ]
}
```

Повтор с `"allow_overlap_own": true` в теле — бронь создаётся (проверка накладок по помещению при этом всё равно выполняется).

201 — создана(ы) со статусом **`BOOKED`**. Ответ включает: `id`, `ids[]`, `count`, `user_id`, `resource_id`, `date`, `time_id`, `time_ids`, `start_time`, `end_time`, `starts_at`, `ends_at`, `status`, `bookings[]`.

| Код | Когда |
|-----|--------|
| 400 | нет периода / битый интервал / разные дни / не по сетке / прошедшее время / несогласованная дата |
| 404 | период / ресурс / пользователь не найден |
| 409 | накладка («уже занято») / **своя бронь на это время в другом помещении** (`conflict: own_overlap`) |
| 422 | валидация тела |

### `POST /bookings/{id}/cancel?user_id=[&token=]`
→ CANCELLED. `user_id` обязателен. Отменить может владелец **или администратор** — по `token` (предпочтительно) либо по `user_id` с ролью `ADMIN`.  
200: `{ id, status: "CANCELLED", date, start_time, end_time, starts_at, ends_at }`  
403 «это не ваша бронь» (обычный пользователь); 404 «бронь не найдена»; 409 «бронь уже отменена» / период уже начался (для всех ролей).  
Без `user_id` → 422.

## Сводная таблица HTTP-кодов

| Код | Смысл |
|-----|--------|
| 200 | Успех чтения / cancel |
| 201 | Создание (user / booking) |
| 400 | Бизнес-валидация (даты, интервалы) |
| 403 | Не владелец (cancel) |
| 404 | Не найдено |
| 409 | Конфликт (накладка, дубль телефона, повторная отмена) |
| 422 | Ошибка схемы FastAPI |

---

## Чего в API нет

- Отдельного `…/reschedule` (перенос на клиенте).
- PATCH / PUT / DELETE.
- Токенной авторизации / сессий.
- Поля `resource_id` в элементах `GET /bookings`.
